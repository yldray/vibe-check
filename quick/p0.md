# Quick mode: every P0 check

Generated by `scripts/build-quick.py` from the checklists. Do not edit by hand.
`manual` = can't be verified from code (device, store console, production, a running build).

## Every project

- `UNI-001` Hardcoded secrets. Test: Run `gitleaks detect --redact` (scans files and git history without printing the values), then grep migrations, seeds, `scripts/`, `deploy/`, `.github/workflows/`, AI instruction files and `git ls-files` output (reports, exports, dumps) for `password|secret|key|token|Server=`. Check `~/.zsh_history` / `~/.bash_history` and `.git/config` remotes for inline credentials.
- `UNI-002` Hallucinated packages. Test: Check every new dependency on the registry: publisher, downloads, age.
- `UNI-003` Auth disabled "for testing". Test: Call every endpoint without a token.
- `UNI-004` Broken object-level authorization (IDOR). Test: Log in as user A, request user B's resource by ID.
- `UNI-005` Client-side-only validation. Test: Send invalid data directly with curl / Postman.
- `UNI-006` Mock data left in production. Test: Search for `mock`, `fake`, `dummy`, `demo`, `simulat`, `lorem`, `TODO`, `FIXME`, `test@`, `example.com`, `picsum`, `pravatar`, `placeholder`, `localhost`. List the production DI registrations (`(Log|Dummy|Fake|Null|InMemory|Console)` implementations). Send one real e-mail, SMS and AI call from production; call every reward and upgrade endpoint with a normal user token.
- `UNI-013` "Done" without the effect. Test: For every terminal status, write a reconciliation query: status = done AND the real effect (row, external record, e-mail log) is missing. Run `SELECT status, COUNT(*) … GROUP BY status` and name the screen, counter and job that handles each value. For every feature in the release, count its success events or rows a few days after launch. Make the downstream call return 400/429/500 and check the status.
- `UNI-014` Save overwrites fields it didn't show. Test: For every edit form, fill every field with distinctive values, save, reload from the server and compare field by field. Send each update endpoint one changed field and diff the full row. Open record A in two tabs, switch to B in one, save in the other. Log each action's payload and compare it with the button label; run bulk actions on 3+ rows.
- `UNI-015` Safety checks that don't stop anything. Test: For every auth, limit, approval and deploy-trust check, force its dependency to fail (revoke the token scope, block the host, delete or lock the DB, empty the config table, put the failing item on page 2). Turn on each kill switch / dry-run / cap = 0 and run every job and endpoint that writes the protected data, then count real writes. Grep each setting key for a reader.
- `UNI-016` A guess instead of "unknown". Test: For each lookup that feeds money, permissions or another system, feed it: no match, two matches, an unconfirmed suggestion, a legitimate `0`, an empty scope. Grep for `ISNULL(`, `COALESCE(`, `??`, `|| <number>`, `MAX(`, `TOP 1` / `FirstOrDefault` without an order, and code that replaces an empty filtered list. List numeric literals in business logic and ask where each comes from.
- `UNI-017` manual · New SQL never run on production-shaped data. Test: Run every new or changed query and script once against a copy of the production schema and a production-sized dataset (or a read replica) before deploy; record errors, duration and the command timeout. Include rollback and diagnostic scripts. Make the endpoint time out and see what the UI shows.
- `AUTH-001` Token decoded, never verified. Test: Take a real token, change the payload (user ID or role), keep the old signature and call a protected endpoint. Also try a token with `"alg": "none"`.
- `AUTH-002` Reset links and one-time codes that live forever. Test: Use a reset link twice; use one after 2 hours; enter 20 wrong codes in a row.
- `AUTH-009` Backdoors left in the production login. Test: Request a code for an address you don't own and read the full response body. Grep code, config and seeds for `devCode`, `debugCode`, `bypass`, `fixed`, `master`, literal 4–6 digit codes and literal passwords. Call every reset endpoint without a valid code. List accounts in the production DB created by a seed, a script or the agent, and try the seed/README passwords on the live login.
- `AUTH-010` Account found by an unnormalized or shared phone or e-mail. Test: Try reset and login with the same phone in five formats and the same e-mail in different case. Count stored values shared by 2+ accounts after normalization. With a second test phone, identify as another test customer using only knowable facts and check whether your number is now on their record.
- `AUTH-011` Role checks that aren't on the endpoint. Test: Log in as the lowest role. Call every admin endpoint directly, also in upper case, with a trailing slash and URL-encoded. Call each invite and role endpoint with every higher role. Call hub methods from a script with a lower role and with the feature switched off.
- `ENV-001` `.env` in `.gitignore`
- `ENV-002` `.env.example` with every key (no values)
- `ENV-003` Separate keys, bot/app tokens, webhooks and databases for dev / CI / staging / prod; production config points at no test host. Test: start the app locally and run the CI evals: production keeps receiving its messages and its balance doesn't move; grep production config for staging/test domains
- `ENV-004` Debug / verbose logging off in prod
- `ENV-005` App fails fast on startup if a required setting is missing, empty or still a placeholder (`changeme`, `<DB>`, `__SET_AT_DEPLOY__`, `YOUR_…`), or still equals the dev value from the base config file. Test: start the production build with each required value removed, set to a placeholder, and with the DB unreachable. Pass: the process exits and names the key; no committed base config holds a working secret; startup logs which source (file, env, machine env var) each critical value came from, without the value
- `OPS-001` Migrations that break production. Test: Generate the SQL before deploying (`dotnet ef migrations script`, `prisma migrate diff`, `alembic upgrade head --sql`) and look for: unescaped quotes inside string literals; new unique indexes or checks (run the matching `GROUP BY … HAVING COUNT(*) > 1` / `WHERE NOT (…)` on production data first); renames, NOT NULL or enum changes with no `UPDATE` for existing rows; hard-coded schema names. Generate a probe migration on a clean branch: it must be empty. Apply to an empty DB and to a copy of production, then read every existing row through the app. Grep startup code for `EnsureDeleted`, `DROP DATABASE`, `sync({force:true})` and for ALTERs or `Migrate()` inside an empty catch.
- `OPS-015` manual · Deploy is green, production runs other code. Test: List every hostname, site, slot and container that serves the app, and every client's base URL. After a deploy, read a version endpoint (build commit) on each and compare it with the commit you pushed. Treat a "skipped" or "queued" deploy run as failed. Build the pushed commit from a clean clone.
- `OPS-018` A rewrite drops what shipped clients still call. Test: List every route and field called by every client version still in use (old backend code + client code + access logs) and call each one against the new backend.
- `OPS-010` No `pull_request_target` workflow checks out or runs code from the pull request: a fork's PR would run with your secrets and a write token
- `OPS-011` No `${{ github.event.* }}` (PR title, issue body, branch name, commit message), `${{ inputs.* }}` (including "type deploy to confirm" inputs), `${{ steps.*.outputs.* }}` or `${{ needs.* }}` value is written straight into a `run:` script; pass it through `env:`, quote the variable and validate its format (`grep -n '${{' .github/workflows/*.yml` inside `run:` blocks)
- `LEGAL-001` Privacy policy published and linked (required by both app stores)
- `LEGAL-002` Users can delete their account and data
- `LEGAL-003` Terms of service published and linked
- `LEGAL-012` If children may use the app: an age check and parental consent where the law asks (COPPA below 13 in the US; GDPR below 16, lower in some countries) and the store family policies are followed
- `QA-008` manual · On production, with a fresh account: sign up, verify, do the main action and pay (if the app takes payments), end to end
- `QA-009` manual · Transactional e-mails arrive in the inbox (not spam) at Gmail, Outlook, Yahoo and iCloud, and every link in them points to production, not localhost (if the app sends e-mail). The sending domain has exactly one SPF record (no `+all`), DKIM set up as the provider says (CNAME vs TXT) and a DMARC record; check `dkim=pass` in the raw headers. Re-test after every hosting, DNS or mail-provider change. Login and reset codes use their own sender, never the mailbox used for bulk mail or load tests
- `SEC-001` Secrets only in env / secret manager
- `SEC-002` Passwords hashed with bcrypt / argon2 (never plain, never MD5/SHA1)
- `SEC-003` Auth + authorization on every protected route
- `SEC-004` Parameterized queries
- `SEC-005` CORS restricted to known origins
- `SEC-012` Codes, tokens, keys and passwords come from a CSPRNG (`RandomNumberGenerator`, `crypto.randomBytes` / `randomInt`, `secrets`), never `Math.random` / `System.Random` / `random.randint` / `Get-Random`, and no token is derived from a user ID. Test: `grep -rnE "new Random\(|System\.Random|Math\.random|Get-Random|random\.randint"` and check every hit that produces a code, token, key, password or salt, including setup and deploy scripts
- `SEC-013` Server-side fetches of user-supplied URLs ("import from URL", link previews, webhooks) refuse internal, metadata (`169.254.169.254`) and private IPv4/IPv6 targets at connect time, including after redirects and DNS rebinding, and stop reading at a size cap. Test: submit `http://169.254.169.254/`, `http://localhost:<port>/`, `http://[::1]/`, `http://[fd00::1]/` and a URL that redirects to `127.0.0.1`

## Frontend (any)

- `FE-001` No secrets in the bundle (search the build output)
- `FE-002` Auth tokens not in `localStorage` if XSS is a risk; prefer HttpOnly cookies
- `FE-013` Production serves the built files, not a dev or preview server: no `vite`, `vite preview`, `npm run dev`, `ng serve`, `vue-cli-service serve`, `webpack serve`, `next dev` or `python -m http.server` in the Dockerfile `CMD`, Procfile, PM2 config, systemd unit or `start` script, and no `allowedHosts` opened for the production domain. Dev servers aren't built for the internet: once exposed, Vite's leaked arbitrary files through `server.fs.deny` bypasses (CVE-2025-31125 is on CISA's Known Exploited list). Test: grep those files; `curl -s https://<site>/ | grep -c "@vite/client"` prints 0 (see `ENV-004`)
- `FE-017` API calls don't depend on the dev server's proxy (`server.proxy` in Vite, `proxy.conf.json` in Angular, `devServer.proxy`, `"proxy"` in a CRA `package.json`): every proxied prefix such as `/api` is routed by the production host, or the app calls the API's own URL with CORS allowing your origin. Otherwise `/api/*` hits the SPA fallback and every call fails with "Unexpected token '<'" or "Http failure during parsing". `vite preview` reuses `server.proxy`, so it hides the problem. Test: on the deployed site, API responses in DevTools → Network are JSON, not `text/html`
