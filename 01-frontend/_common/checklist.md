# Frontend — common checks

- [ ] `FE-001` **P0** No secrets in the bundle (search the build output)
- [ ] `FE-002` **P0** Auth tokens not in `localStorage` if XSS is a risk; prefer HttpOnly cookies
- [ ] `FE-003` **P1** Works on Chrome, Safari, Firefox and mobile Safari
- [ ] `FE-004` **P1** Responsive at 360px, 768px and 1440px
- [ ] `FE-005` **P1** Loading, empty and error states on every data view
- [ ] `FE-006` **P1** Forms: double submit blocked, errors shown, server errors handled
- [ ] `FE-007` **P1** Back button and page refresh don't break state
- [ ] `FE-008` **P1** Every public page has its own `<title>` and meta description that say what the page is (about 50–60 and 150–160 characters), not the template default (`Vite + React`, `React App`, `Create Next App`, `Home`) or one pair shared by every route. An SPA sets them per route (`react-helmet-async`, Next.js `metadata`, Angular `Title` and `Meta`, Nuxt `useHead`), and public pages are prerendered or server-rendered so crawlers that don't run JavaScript see them. Test: `curl -s https://<site>/<path> | grep -iE '<title>|name="description"'` on three different pages: the values differ and none is a default (see `FE-019`, `FE-020`, `FE-021`)
- [ ] `FE-009` **P2** Favicon and app icons
- [ ] `FE-010` **P1** No errors in the browser console on production pages (missing files, failing third-party scripts, hydration errors). Test: open the main pages with DevTools open; PageSpeed Insights doesn't list "Browser errors were logged to the console"
- [ ] `FE-011` **P2** Run PageSpeed Insights (Mobile and Desktop) on the main pages before launch and work through every listed item under Performance, Accessibility and Best Practices, not just the score
- [ ] `FE-012` **P2** Production stack traces are readable: source maps are uploaded to the error tracker (hidden, not served publicly); structured data (JSON-LD), if any, passes Google's Rich Results Test. Test: `curl -s -o /dev/null -w "%{http_code}" https://<site>/assets/<bundle>.js.map` returns 404 and served JS has no `sourceMappingURL` comment (Vite `build.sourcemap` is `false` or `'hidden'`; maps are deleted from the deploy after upload)
- [ ] `FE-013` **P0** Production serves the built files, not a dev or preview server: no `vite`, `vite preview`, `npm run dev`, `ng serve`, `vue-cli-service serve`, `webpack serve`, `next dev` or `python -m http.server` in the Dockerfile `CMD`, Procfile, PM2 config, systemd unit or `start` script, and no `allowedHosts` opened for the production domain. Dev servers aren't built for the internet: once exposed, Vite's leaked arbitrary files through `server.fs.deny` bypasses (CVE-2025-31125 is on CISA's Known Exploited list). Test: grep those files; `curl -s https://<site>/ | grep -c "@vite/client"` prints 0 (see `ENV-004`)
- [ ] `FE-014` **P1** A deploy doesn't break tabs that are already open: the previous build's hashed JS and CSS stay online for a few days, `index.html` is sent with `Cache-Control: no-cache`, and a failed lazy chunk (`vite:preloadError`, webpack `ChunkLoadError`, "Failed to fetch dynamically imported module") reloads the page once instead of leaving a blank screen. Test: open the app, deploy a build that changes a lazily loaded page, then open that page in the same tab (see `PERF-011`)
- [ ] `FE-015` **P1** A service worker can't keep users on an old release: `sw.js` changes with every build (a generated precache list with file hashes, e.g. Workbox or `vite-plugin-pwa`), page HTML is fetched network-first, and an update applies on the next load or through a working "Update" prompt. A removed service worker is replaced by one that unregisters itself, because a 404 for `sw.js` leaves the old one running. Test: deploy a visible change, reload twice and reopen the installed app; DevTools → Application → Service workers shows no version stuck on "waiting"
- [ ] `FE-016` **P1** Client config is fixed at build time: `VITE_*`, `NEXT_PUBLIC_*`, `REACT_APP_*` and Angular `environment*.ts` values are written into the bundle, so env vars set on the running container change nothing, and one image promoted from staging keeps calling the staging API. Test: search the JS files production serves for API origins: only production hosts, no `localhost` or staging host (see `UNI-018`, `ENV-003`)
- [ ] `FE-017` **P0** API calls don't depend on the dev server's proxy (`server.proxy` in Vite, `proxy.conf.json` in Angular, `devServer.proxy`, `"proxy"` in a CRA `package.json`): every proxied prefix such as `/api` is routed by the production host, or the app calls the API's own URL with CORS allowing your origin. Otherwise `/api/*` hits the SPA fallback and every call fails with "Unexpected token '<'" or "Http failure during parsing". `vite preview` reuses `server.proxy`, so it hides the problem. Test: on the deployed site, API responses in DevTools → Network are JSON, not `text/html`
- [ ] `FE-018` **P1** If the app is served under a subpath (`/app/`, GitHub Pages), the build's base path matches: `base` in Vite, `--base-href` in Angular, `basename` in React Router, `app.baseURL` in Nuxt, and the router's history uses it. Test: open the deployed URL and a deep link; no asset 404s, no blank page
- [ ] `FE-019` **P1** Search engines are let in on production: `robots.txt` doesn't say `Disallow: /`, and no page carries `<meta name="robots" content="noindex">` or an `X-Robots-Tag: noindex` header left over from staging (staging, in turn, keeps them). `/sitemap.xml` lists only public pages that answer 200, with absolute production URLs (no `localhost`, staging or preview host), and `robots.txt` names it in a `Sitemap:` line. Test: `curl -s https://<site>/robots.txt`; `curl -sI https://<site>/ | grep -i x-robots-tag` prints nothing; open the sitemap and spot-check URLs; `curl -sI` on `/robots.txt` and `/sitemap.xml` shows a text or XML `content-type`, not the SPA's `index.html`
- [ ] `FE-020` **P1** Every indexable page has a `<link rel="canonical">` with its own absolute production URL. AI puts one canonical tag in the shared layout, so every page names the home page and search engines drop the rest; or the tag points to `localhost`, a staging host, `http://`, or the other one of `www` and the bare domain (see `WEB-018`). Pages reached with query strings (filters, `?utm_source=`) point to the clean URL. Test: `curl -s https://<site>/<path> | grep -i 'rel="canonical"'` on the home page and two inner pages: each prints its own URL
- [ ] `FE-021` **P2** A shared link shows a proper preview: each public page has `og:title`, `og:description`, `og:image` and `twitter:card` (`summary_large_image`). `og:image` is an absolute `https://` URL on the production domain (a relative path or `localhost` breaks the preview), about 1200×630, under 5 MB and reachable without a login. Test: paste the URL into LinkedIn Post Inspector or opengraph.xyz and send it in a chat app: the image and title appear
- [ ] `FE-022` **P1** No broken links: no placeholder `href="#"` or `javascript:void(0)` in the navigation, footer or buttons; no link to a page that was never built (AI writes footers with About, Careers, Blog, Privacy and Terms that lead nowhere); external links (social profiles, docs, store badges) open the right page. An SPA answers 200 for every path, so a crawler misses its dead routes: also click each navigation and footer link and look for your 404 page. Test: `npx linkinator https://<site> --recurse` (or `lychee`) reports no broken links, and `grep -rn 'href="#"' src/` finds no placeholders
- [ ] `FE-023` **P2** The landing page has one clear main call to action: visible without scrolling at 360px, worded as the outcome ("Start free trial", "Book a demo") instead of "Submit", "Click here" or "Learn more", and stronger than the other buttons. It leads to a working next step (sign-up, checkout, contact form), not `#`. AI landing pages often show three equal buttons with vague labels. Test: open the home page on a phone; a first-time visitor can say within five seconds what the button does, and pressing it reaches that step (see `FE-022`, `QA-002`)
- [ ] `FE-024` **P1** A site that sells or signs people up has an FAQ (a page, or a section linked from the footer and the pricing page) answering what people ask before paying: price and what's included, trial, cancellation and refunds, data and privacy, how to reach support. Every answer matches the real terms: AI writes generic answers ("cancel anytime", "30-day money-back guarantee", "end-to-end encrypted") that the product, the checkout and the published policies don't back up (see `LEGAL-007`, `LEGAL-017`). If the page uses `FAQPage` structured data, it repeats the visible questions and answers word for word; don't count on a Google rich result, which since 2023 shows only for well-known government and health sites. Test: read each answer next to the pricing page, the checkout and the refund, cancellation and privacy policies: any mismatch fails
- [ ] `FE-025` **P2** If AI assistants should read the site, `/llms.txt` follows the llmstxt.org format: an H1 with the site's name, a `>` one-line summary, then sections of links to the key public pages (ideally to clean Markdown versions). It lists only public URLs (no admin, staging or API routes) and is served as text, not the SPA's `index.html`. It's a proposal that AI tools are starting to read, not a search ranking factor, and `robots.txt` still decides which crawlers may fetch pages (see `FE-019`). Test: `curl -sI https://<site>/llms.txt` shows 200 and a `text/plain` or `text/markdown` content type; every link in it opens
