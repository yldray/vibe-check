# Windows server and IIS

Only if the app is deployed to Windows: IIS, `web.config`, Windows services, Task Scheduler or PowerShell deploy scripts.

### WIN-001 · `web.config` that IIS rejects, and a 404 page that answers 200
**Severity:** P1
**Why it breaks:** AI writes `web.config` on a machine where everything is installed and allowed, then copies it to the server. A section the server doesn't know (`<rewrite>` without the URL Rewrite module, `<aspNetCore>` without the ASP.NET Core Hosting Bundle) or one it locks (authentication sections such as `windowsAuthentication`, the `defaultPath` attribute of `httpErrors`, an absolute path to an error page) makes IIS answer 500.19 for every URL of the site, not only for the feature that needed it. Custom error pages have their own trap: `httpErrors` with `responseMode="ExecuteURL"` pointing at a static `.html` file answers 200, so every broken link is indexed as a real page and a smoke test that expects 404 sees success.
**How to test:** Right after copying a new `web.config`, request the home page and one API route and read the status (`curl -s -o /dev/null -w '%{http_code}' https://<site>/`). On a 500.19, open the page in a browser on the server itself: the detailed error names the config line, with `0x80070021` for a locked section and `0x8007000d` for an unknown one. Compare the sections in `web.config` with the installed modules (`Get-WebGlobalModule`, or IIS Manager → Modules). `curl -s -o /dev/null -w '%{http_code}' https://<site>/no-such-page` must print 404.
**Pass:** Every config change is loaded right after the copy and the deploy fails on a 500; a missing page shows the custom page with status 404.
**Fix:** Install the modules the config uses during server setup (URL Rewrite, Hosting Bundle, Application Initialization) and check for them before the deploy copies the config. Keep locked settings in server-level config, or unlock them at server level on purpose. Use `responseMode="File"` for static error pages, or an error page in the app that sets the status code. Fail the deploy on a 500, and on a 200 for a missing page. See `WEB-011`, `OPS-006`.

### WIN-002 · The first request after a deploy, recycle or reboot is slow
**Severity:** P2
**Why it breaks:** IIS starts the app only when the first request arrives, stops it after 20 idle minutes (the app pool's default `idleTimeout`) and recycles the pool every 1,740 minutes by default. The first user after each deploy, recycle or quiet night waits seconds for startup, sometimes past the client's timeout, and a scheduler hosted inside the app doesn't run while the app is stopped. AI sets the pool to `startMode="AlwaysRunning"` and stops there, but that only starts the worker process. The app itself still waits for a request unless the application is preloaded, and preloading needs the Application Initialization module, a separate IIS feature that is often not installed.
**How to test:** Recycle the pool (`Restart-WebAppPool <pool>`) or redeploy, wait a minute, then time the first and second requests to the login and admin pages (`curl -o /dev/null -s -w '%{time_total}' <url>`). Check `Get-WindowsFeature Web-AppInit`, the pool's `startMode` and `idleTimeout`, and the application's `preloadEnabled`.
**Pass:** The first request is about as fast as the second.
**Fix:** `Install-WindowsFeature Web-AppInit`, `startMode="AlwaysRunning"` on the pool, `preloadEnabled="true"` on the application, and `idleTimeout` 0 for apps that run jobs. Add an `<applicationInitialization>` warm-up page in `web.config` if startup work happens on first use. Schedule recycles off-peak, and have the deploy send a warm-up request before it reports success. See `OPS-004`, `OPS-006`.

### WIN-003 · Setup scripts fight the certificate renewal tool
**Severity:** P1
**Why it breaks:** One tool renews the certificate (win-acme, Certify The Web, a scheduled script) and a setup or deploy script AI wrote "to make HTTPS work" binds it. The script looks in the wrong store (`Cert:\LocalMachine\My`, while win-acme on an IIS server uses `WebHosting` by default), finds nothing and generates a self-signed certificate with `New-SelfSignedCertificate`. Or it rebuilds the bindings on every run with the first certificate it finds, which may be the expired one. After the next renewal or deploy the site serves an expired or self-signed certificate, and every browser and API client refuses it.
**How to test:** Read every script that touches bindings (`New-WebBinding`, `.AddSslCertificate(<thumbprint>, '<store>')`, `netsh http add sslcert`, `IIS:\SslBindings`). Force one renewal (`wacs --renew --force`), run the setup and deploy scripts, then check what each hostname serves: `echo | openssl s_client -connect <host>:443 -servername <host> 2>/dev/null | openssl x509 -noout -subject -issuer -enddate`.
**Pass:** After a forced renewal and a script run, every hostname serves the newest certificate from the real CA; a second run of the script changes nothing.
**Fix:** One owner for bindings: the renewal tool's IIS step, or the script, reading the store the renewal tool writes to and picking the certificate by hostname and latest expiry. The script leaves a valid binding alone and never creates a self-signed certificate on a production host: it fails with a message instead. An expiry alert watches the served certificate. See `WEB-001`, `CLOUD-011`.

### WIN-004 · Service settings applied only when the service is created
**Severity:** P1
**Why it breaks:** `DB-002` and `DOTNET-033` cover what a service needs to survive a reboot: start type, a dependency on the database service, recovery actions and the failure flag. On Windows the gap is usually the deploy script. AI wraps `New-Service` or `sc.exe create` in `if (-not (Get-Service ...))` and puts the `sc.exe config` and `sc.exe failure` lines in the same block, so later fixes never reach a server where the service already exists. In PowerShell, `sc` without `.exe` is the alias of `Set-Content`, so `sc config ...` never touches the service. `sc.exe` needs a space after each `=` (`start= delayed-auto`) and reports failure only through its exit code, and Windows PowerShell 5.1's `Set-Service` has no `AutomaticDelayedStart`.
**How to test:** Grep deploy scripts for `sc ` without `.exe`, for `sc.exe config` or `failure` inside an "if not exists" block, and for `AutomaticDelayedStart`. After a deploy, compare `sc.exe qc <svc>`, `sc.exe qfailure <svc>` and `sc.exe qfailureflag <svc>` with what the script means to set.
**Pass:** Every deploy applies the service settings, checks `$LASTEXITCODE` after each `sc.exe` call, and the live settings match the script.
**Fix:** Create the service only if it is missing, then apply start type, dependency, recovery and failure flag on every deploy. Always write `sc.exe`, and stop on a non-zero exit code. See `DB-002`, `DOTNET-033`, `OPS-016`.

### WIN-005 · Scheduled tasks run at the wrong hour
**Severity:** P1
**Why it breaks:** Nobody chose the server's time zone: a cloud image starts in UTC, a hand-installed server in whatever the installer picked, so a task meant for 02:00 local runs hours off. Task Scheduler also stores each trigger's `StartBoundary` either as local time or with a UTC offset (or `Z`), which is the "Synchronize across time zones" box, and triggers registered from PowerShell often have it on without anyone choosing it. A trigger with an offset keeps firing at the same UTC moment, so after someone fixes the server's zone, or across a daylight-saving change, it runs at another local hour and nobody notices because it still runs daily.
**How to test:** On each server read the zone (`tzutil /g` or `Get-TimeZone`) and compare it with the zone the schedules were written for. For each task, run `Export-ScheduledTask -TaskName <name>` and read `StartBoundary`: an ending like `+03:00` or `Z` pins it to UTC. Compare `NextRunTime` from `Get-ScheduledTaskInfo -TaskName <name>` with the intended local time.
**Pass:** The setup script sets the zone on purpose (`Set-TimeZone -Id`), and every task's next run time matches the intended business time.
**Fix:** Set the zone in server setup. Write `StartBoundary` without an offset when the task should follow local time, or with one on purpose and documented. Re-register every task after changing the zone. Alert on `LastTaskResult` and on the last run time. See `OPS-008`, `OPS-004`.
